# 系统架构

## 总体分层

当前项目可以按四层理解：

1. 启动层：`main.c`、`int_user.c`
2. 中断与周期任务层：`isr.c`、`a_run.c`
3. 控制与策略层：`ADC.c`、`imu.c`、`pid.c`、`a_run_mode.c`、`motor.c`、`FUYA.c`
4. 配置与调试层：`eeprom.c`、`menu.c`、`vofa.c`、`debug_view.c`

## 启动执行链

启动流程如下：

```text
main
  -> clock_init
  -> debug_init
  -> int_user
       -> hardware_init
       -> control_init
       -> app_init
```

`hardware_init()` 负责外设、EEPROM、定时器、编码器、ADC、电机、负压和无线串口初始化。  
`control_init()` 负责 PID 控制器初始化，并调用 `control_apply_config()` 把 `g_app_capp_config步到运行时控制器。  
`app_init()`当前主要做`offset_init()`，用于上电后 IMU 偏置准备。

## 定时器与中断链

当前实际投入使用的核心周期链有两条：

```text
TM0_IRQHandler
  -> run_time_1

TM1_IRQHandler
  -> run_time_2
```

职责划分：

- `run_time_1()`：高频控制主链
  - IAP 保护脚处理
  - 电感采样
  - 传感器准备
  - 编码器读取
  - 转向环计算
  - 飞坡速度逻辑
  - 角度环计算
  - 左右速度环计算
  - 电机输出
- `run_time_2()`：较低频的监测与状态更新
  - 电感最大值扫描
  - 丢线检测
  - 电压检测
  - 姿态更新
  - 起跑状态更新
  - 负压状态更新

`run_time_3()` 当前存在于代码中，但并未接入定时器中断主链，更多像实验性或备用控制路径。

## 主循环职责边界

主循环当前是低优先级服务层，不承担核心控制。

编译开关位于 `main.c`：

- `MAIN_ENABLE_VOFA`
- `MAIN_ENABLE_MENU`
- `MAIN_ENABLE_SPEED_TEST`

主循环可以按需要开启：

- `debug_vofa_service()`
- `Keystroke_Menu()`
- `printf_speed_test()`

比赛态通常不建议开启高频串口打印和重调试逻辑。

## 参数流转

当前配置流已经统一成一条清晰链路：

```text
menu / vofa
  -> app
  -> control_apply_config
  -> PID
  -> config_save / config_load
  -> EEPROM
```

可以这样理解：

- `app`：配置真值
- `PID`：当前运行控制器参数副本
- `EEPROM`：掉电持久化存档

### 修改参数时

1. 菜单或 VOFA 改动 `g_aapp_config
2. 调用 `control_apply_config()`
3. 运行中的 PID 立即更新

### 保存参数时

1. 调用 `config_save()`
2. 先把当前配置再应用一次
3. 调用 `eeprom_flash()` 持久化

### 读取参数时

1. 调用 `config_load()`
2. `eeprom_init()` 从 EEPROM 恢复 `g_app_config
3. `control_apply_config()` 同步到 PID

## 中断与主循环的边界约束

当前项目遵循这条原则：

- 中断路径优先做实时控制
- 主循环优先做调试与人机交互

这带来的要求是：

- 中断中避免引入重打印、阻塞等待和复杂文本解析
- 主循环的菜单和 VOFA 不能成为比赛态必需路径
- 跨中断与主循环共享的状态应显式处理，避免优化器误判

## 当前模块依赖骨架

```text
main
  -> int_user
  -> menu / vofa / debug_view

int_user
  -> eeprom
  -> imu
  -> pid
  -> motor
  -> FUYA

isr
  -> a_run

a_run
  -> ADC
  -> imu
  -> pid
  -> motor
  -> a_run_mode

a_run_mode
  -> FUYA
  -> eeprom

menu / vofa
  -> eeprom
  -> int_user
  -> pid
```

## 架构上的关键取舍

当前结构没有追求“文件越多越好”，而是更偏向比赛项目的实际可用性：

- 把初始化分层，但不改启动顺序
- 把配置收成结构体，但不改变 EEPROM 地址布局
- 把模式逻辑从 `a_run.c` 中拆出一部分，但不破坏中断主链阅读路径

后续优化应继续遵循这个方向：  
优先让结构更清楚，但不要为了抽象而牺牲实时性和现场调车效率。
