# 双十字元素设计

## 概要

新增一个独立的“双十字”赛道元素，接入现有元素序列仲裁链路。

该元素的目标是：

- 使用与墙面相同的入口电感判定方式；
- 进入后只负责屏蔽后续元素识别；
- 不改速度、不改转向目标；
- 当编码器积分达到设定阈值后结束，开放下一个元素。

本次设计优先保持现有“元素独立状态机，仲裁层只调度”的结构，不把双十字逻辑混入墙面或仲裁主文件内部。

## 需求边界

### 已确认需求

- 双十字是新的独立元素编号。
- 入口条件使用墙面同款电感和阈值：
  - `ad1 + ad2 + ad3 + ad4 > 100`
- 结束条件是编码器积分达到阈值。
- 编码器阈值走 EEPROM 可调参数。
- 双十字元素本身不额外降速，不覆盖速度目标，不覆盖转向目标。

### 非目标

- 本次不把双十字入口阈值改成 EEPROM 参数。
- 本次不新增双十字专用降速逻辑。
- 本次不改变墙面、圆桶、圆环、跷跷板已有入口和退出行为。
- 本次不调整元素仲裁顺序规则，只新增一个可被序列选择的元素类型。

## 设计选择

### 方案对比

#### 方案 A：独立双十字状态机

新增 `a_run_cross.c/.h`，由元素仲裁按序调用。

优点：

- 与现有圆环、圆桶、墙面结构一致；
- 逻辑职责清楚，便于单独调试；
- 后续如果要加二次确认或额外退出条件，改动边界清晰。

代价：

- 需要增加一个模块、一个元素编号、一组 EEPROM 配置和菜单项。

#### 方案 B：复用墙面状态机增加模式分支

在墙面模块里增加“双十字模式”，共用入口判定，退出切成编码器积分。

优点：

- 文件数更少。

代价：

- 墙面模块将同时承担两种退出机制；
- 墙面与双十字耦合增加，后续现场排障更难分辨问题来源。

#### 方案 C：仲裁层直接内联双十字逻辑

在 `a_run_track_element.c` 中直接维护双十字状态。

优点：

- 改动文件最少。

代价：

- 仲裁层开始承载元素内部细节，破坏现有边界；
- 后续再加调参或状态扩展会继续挤大仲裁文件。

### 采用方案

采用方案 A：独立双十字状态机。

原因：

- 最贴合当前仓库的元素组织方式；
- 对高频控制链路影响最小；
- 修改范围可控，便于验证和回归。

## 结构设计

### 1. 元素编号与仲裁接入

在 `a_run_track_element.h` 中新增双十字元素编号，例如：

- `TRACK_ELEMENT_CROSS 6`

同时在 `a_run_track_element.c` 的可执行元素判断、元素枚举和主仲裁 `switch` 中接入该元素。

接入后，双十字可以像当前左环、右环、圆桶、墙面、跷跷板一样出现在 `app.start.element_seq[]` 中，由元素序列串行开放。

### 2. 双十字模块

新增：

- `project/user/a_run_cross.h`
- `project/user/a_run_cross.c`

对外接口保持和墙面、圆桶一致的轻量风格：

- `void a_run_cross_reset(void);`
- `uint8 a_run_cross_update_5ms(void);`
- `int8 a_run_cross_get_state(void);`

其中 `update` 返回值语义保持一致：

- `1` 表示双十字流程完成，可开放下一个元素；
- `0` 表示仍在当前元素流程中。

## 状态机设计

双十字采用三阶段状态机：

### `CROSS_IDLE`

职责：

- 刚进入双十字元素时清零内部状态；
- 清零编码器积分；
- 清零入口连续命中计数；
- 然后切到 `CROSS_WAIT_SIGNAL`。

### `CROSS_WAIT_SIGNAL`

职责：

- 每个 2ms 周期计算四路电感和；
- 当 `ad1 + ad2 + ad3 + ad4 > 100` 连续命中达到规定次数后，进入积分阶段。

建议保留与墙面一致的 2 次连续确认：

- `CROSS_SIGNAL_CONFIRM_COUNT 2u`

这样可以滤掉单拍毛刺，同时不引入明显响应延迟。

### `CROSS_TIMING`

职责：

- 使用当前已有元素模块的编码器积分口径累计里程；
- 不覆盖 `speed`；
- 不覆盖 `angle_target`；
- 当积分达到 `app.cross.encoder_target` 时结束该元素。

结束时调用 `a_run_cross_reset()` 并返回 `1`。

## 判定与积分口径

### 入口判定

双十字入口固定使用四路归一化电感和阈值：

- `CROSS_AD_SUM_THRESHOLD 100u`

实现上直接复用墙面当前确认方式：

- 先算 `ad_sum = ad1 + ad2 + ad3 + ad4`
- `ad_sum > 100` 才算一次命中
- 连续命中 `2` 次后进入积分阶段

这样可以保证双十字和墙面对“强信号区”的理解一致。

### 结束积分

双十字结束条件使用编码器积分到阈值：

- `cross_encoder_sum >= app.cross.encoder_target`

积分口径建议复用现有元素状态机里已经在用的左右轮速度积分方式，不单独发明新单位。

这样做的原因是：

- 现场调参时不用记两套积分单位；
- 保持与当前圆环/圆桶等模块的编码器尺度一致；
- 减少理解和验证成本。

## EEPROM 与菜单设计

### EEPROM 配置

新增一组双十字配置：

```c
typedef struct
{
    float encoder_target;
} AppCrossConfig;
```

并在 `AppConfig` 中增加：

- `AppCrossConfig cross;`

本次只增加一个参数：

- `encoder_target`：双十字退出积分阈值

### 默认值

默认值先给一个保守可跑的初值，后续现场调参再修正。

建议先设为与当前赛道实际单位相容的中间值，例如：

- `config->cross.encoder_target = 20.0f;`

这里的具体数值属于首版默认值，不代表最终赛道最优值，但需要保证首次烧录后行为可观测、可调。

### 菜单接入

在 `YUANSHU` 下新增 `CROSS` 子页。

该页只显示一个参数：

- `encoder_target`

本次不把入口阈值、确认次数做成菜单项，避免现场调参项继续膨胀。

### 元素序列页

元素序列设置页需要允许新的双十字编号值，便于将其插入 `E1 ~ E6` 任意槽位。

## 数据流与调用链

运行时调用关系保持当前模式：

1. `run_time_1()` 调用 `a_run_track_element_update_gate(...)`
2. 元素仲裁根据 `expected_element` 判断当前是否轮到双十字
3. 若当前元素为双十字，则调用 `a_run_cross_update_5ms()`
4. 双十字完成后返回 `1`
5. 仲裁推进到下一个序列元素

双十字模块内部不直接操作菜单、不直接读 EEPROM 缓冲、不新增控制链路旁路。

## 错误处理与约束

考虑到本项目以实时性优先，本次只保留最小必要约束：

- `encoder_target <= 0` 时在读取配置后回退到默认值；
- 入口连续命中被打断时清零确认计数；
- 双十字完成或复位时清零内部积分，避免上一次残留影响下一次。

不增加额外的超时退出和复杂保护分支，避免让状态机无端变重。

## 风险与取舍

### 风险

- 默认 `encoder_target` 初值可能与赛道实际长度不完全匹配，需要现场试跑后再收敛。
- 如果双十字强信号区和墙面波形很像，元素序列顺序仍然决定谁先开放识别；本次不改变现有串行仲裁原则。

### 取舍

- 这次不做“阈值也可调”，减少 EEPROM 和菜单膨胀。
- 这次不做“进入后自动降速”，保持双十字只是一个纯门控元素。
- 这次不与墙面模块复用状态机分支，优先保留模块清晰度。

## 成功标准

满足以下条件即可认为本次实现完成：

- 双十字可作为新的独立元素插入元素序列；
- 命中四路电感和阈值后进入双十字流程；
- 流程期间不改速度和转向主链；
- 编码器积分到 `app.cross.encoder_target` 后退出；
- 菜单中可调双十字编码器阈值；
- 工程编译通过且无新增告警。
