# 已知问题与优化清单

## 1. 负压计算值和实际输出值可能不一致

- 问题现象：`FUYA` 模块内部计算了 `fuya_date`，但最终输出路径更偏向固定配置值
- 涉及模块：`FUYA`
- 当前判断：需要进一步确认最终输出是否确实应该使用计算结果而不是单一配置值
- 建议处理方向：在不破坏比赛稳定性的前提下，梳理“计算值”和“实际输出值”的设计意图

## 2. 电机输出与保护逻辑仍有收敛空间

- 问题现象：电机输出命名和左右轮映射存在理解成本，保护触发后的输出策略也需要再确认
- 涉及模块：`motor`
- 当前判断：更适合在下一轮专门做“输出语义 + 保护行为”整理
- 建议处理方向：明确左右轮命名、停车策略、计数恢复策略

## 3. 菜单仍然偏阻塞式调试实现

- 问题现象：菜单包含阻塞式页面循环和调试打印
- 涉及模块：`menu`
- 当前判断：适合调车，不适合比赛态常开
- 建议处理方向：保留现有可用性，后续若要长期优化再考虑做轻量状态机

## 4. VOFA 仍然偏重调试态实现

- 问题现象：当前实现使用 `atof`、文本解析和较多打印
- 涉及模块：`vofa`
- 当前判断：调试方便，但对 `8051/C251` 不够轻
- 建议处理方向：比赛态默认关闭；如果后续追求极限体积和实时性，再考虑做轻量协议

## 5. `run_time_3()` 仍是备用路径

- 问题现象：代码中存在 `run_time_3()`，但当前中断主链未使用
- 涉及模块：`a_run`
- 当前判断：属于实验性或备用控制路径
- 建议处理方向：保留时应明确用途；若长期不用，可考虑归档或用编译开关隔离

## 6. 全局运行态仍然偏散

- 问题现象：项目已收拢配置，但部分运行时状态仍散落在多个模块
- 涉及模块：`ADC` `imu` `a_run` `motor` `FUYA`
- 当前判断：当前状态可用，但后续再加功能时会继续增加理解成本
- 建议处理方向：保持小步收敛，优先整理共享状态的语义和边界，不要一次做过度抽象

## 7. 历史 VOFA 文档与当前实现存在偏差

- 问题现象：`project/code` 下旧文档中的接入方式、示例命令和当前代码不完全一致
- 涉及模块：文档与 `vofa`
- 当前判断：旧文档只适合作历史材料
- 建议处理方向：后续维护统一以 `docs/` 下新知识库为准
