# Air Dual Speed Loop PID Tuning Rules

这份文档只记录“架空双轮 `air-dual` 后续新对话默认沿用的调参方法”，不记录每一轮的原始过程。
每次出现新经验时，先写进 `debug_memory.md`；只有重复验证过的结论，才升级到这里。
带负载双轮请改读 `ground_dual_tuning_rules.md`。

## 目标

- 目标不是给每个速度单独找一套 PID。
- 目标是分别给左轮、右轮各找一组“多速度共用”的速度环 PID。
- 左右轮 PID 可以不同。
- 评价重点是多个速度段都能稳定可用，而不是某一个速度点最漂亮。

## 默认调试环境

- 端口：`COM8`
- 模式：架空 `air-dual`
- 负压：关闭，固定 `AT_FUYA=0`
- 保存：默认不发送 `SAVE`
- 默认先调更差的那一侧，当前经验上优先看左轮

## 默认速度序列

当前默认使用两组回归序列。

第一组：
- `15:500,25:500,35:500,45:500,35:500,25:500,15:500`

第二组：
- `15:300,25:300,35:300,45:300,35:300,25:300,15:300`

使用建议：
- 第一组优先用于主评分和稳态观察
- 第二组优先用于更快节奏下的补充验证
- 每轮尾部都补一条 `TEST_speed=0`

说明：
- 这里按当前约定，用户输入中的 `45:50035:500` 解释为 `45:500,35:500`
- 同理，`45:30035:300` 解释为 `45:300,35:300`

## 单轮隔离规则

调左轮时：
- 左轮使用待测 PID
- 右轮固定 `0/0/0`

调右轮时：
- 右轮使用待测 PID
- 左轮固定 `0/0/0`

这样做的目的：
- 降低另一侧对评分的污染
- 方便把问题归因到当前被调的那一侧

## 异常样本处理规则

以下样本当前默认不直接拿来判定 PID 好坏：

- `miss`
  - 先忽略
  - 不直接当作“该组 PID 很差”
  - 先看是不是采样窗口、切段边界或链路噪声导致

- 编码器速度绝对值大于 `200`
  - 直接视为异常样本
  - 不参与评价和趋势判断
  - 原因是已实测：轮子占空比最大时，编码器值也不会超过 `200`

- 整轮 `target=0` 且试验未真正拉起
  - 判定为“试验未启动”
  - 该轮作废
  - 不参与参数排序

## 结束判据

架空 `autotune` 下，不再把 `stop_flag` 作为主结束判据。

默认结束判据是：
- 尾部显式发送 `TEST_speed=0`
- 观察最后一段样本是否连续回零

`stop_flag` 只作为辅助参考，不作为主判断依据。

## 评分与分析习惯

- 当前仍沿用脚本里的现有评分规则
- 重点关注：
  - 起速
  - 超调
  - 稳定时间
  - 稳态误差

分析时默认做法：
- 单轮隔离评分
- 先看分段表现，再看总分
- 更关注重复验证后是否稳定，而不是单次最低分

## 参数调整顺序

默认顺序：
1. 先调 `Kp`
2. 再调 `Ki`
3. 最后才考虑 `Kd`

当前默认经验：
- 左轮保守基线：`100 / 20 / 0`
- 右轮保守基线：`105 / 20 / 0`
- `Kd > 0` 当前不是默认优先方向
- 左轮主要矛盾常出现在低速起步段

## 当前推荐流程

1. 先确认链路稳定
- `INFO!` 正常
- `Parser: frame_overflow_count, queue_overflow_count` 不增长
- 不再出现整轮 `target=0`

2. 再做单轮隔离搜索
- 左轮调试时右轮设 `0/0/0`
- 右轮调试时左轮设 `0/0/0`
- 每次只改一小步邻域

3. 对每侧候选做重复验证
- 不接受只靠单次最低分直接定最终值
- 至少复验前几名候选

4. 把单轮最优候选放回双轮同跑
- 做整车 A/B
- 如果单轮更优、整车更差，则回退到整车更稳的组合

## 当前默认结论

截至当前会话，默认保留：
- 左轮：`100 / 20 / 0`
- 右轮：`105 / 20 / 0`

原因：
- 左轮这轮没有稳定跑出比 `100/20/0` 更稳的新值
- 右轮单轮隔离里曾出现 `106/19/0` 略优
- 但放回双轮同跑后，`106/19/0` 整车表现反而不如基线
- `99/20/0` 在部分轮次里有潜力，但目前只保留为候选，不升级为默认
- `100/19.5/0` 在左轮单轮隔离里也出现过改善，但整车交错复验后仍未稳定压过基线

## 文档更新规则

后续新结论按以下顺序沉淀：

1. 先写 `debug_memory.md`
- 记录目标、条件、已验证事实、推断、下一步

2. 再决定是否升级到本文件
- 只有重复验证过的规则，才写进这里

3. 如果新结论推翻旧规则
- 不删除旧历史
- 在 `debug_memory.md` 里明确标注“已替代”
